## 증상

에이전트 PC 한 대가 지정한 서버(golgong.com)로 가지 못하고 다른 서버(public.o5l3.com)에 눌러앉았다. 같은 증상이 다른 PC에서도 재현됐다. 증상은 겉보기에 세 가지로 보였지만 조사해 보니 하나의 연쇄였다.

| # | 증상 | 상태 |
|---|---|---|
| 1 | UI 조작 없이 서버가 자동으로 public.o5l3.com으로 바뀜 | 미규명 |
| 2 | 그 상태에서 UI로 golgong.com으로 바꿔도 반영되지 않음 | 판명 |
| 3 | 새 버전으로 업데이트되면 온라인 상태가 되지 않음 | 판명 |

## 연쇄 흐름

문제 PC에서 일어난 일을 시각순으로 맞춰 보면 다음과 같다.

1. `set.SETTINGS` 명령으로 서버가 `public.o5l3.com`으로 바뀐다 (증상 1, 발신자는 아직 미상)
2. 등록이 성공하면서 `ApplyServerProfile`이 `UpdateUrl`을 새 서버 주소로 교체한다
3. 약 1분 뒤 `CheckUpdate`가 새 서버의 패키지를 내려받는다. 이때 버전이 더 낮은 패키지(이하 498)로 내려간다
4. 498이 설치된다. 설정 저장소 파일을 텍스트로 읽으려다 실패하면서 `s_bReady = false`로 자기 자신을 멈춘다
5. 이후 설정 저장소를 다루는 모듈(`CAppStore`)이 전면 정지한다 (증상 2, 3)

## 근본 원인 — 저장소 포맷 세대 비대칭

설정 저장소 파일(`registry.ini`)의 내부 포맷은 세대별로 다른데, 두 세대가 같은 파일 이름을 그대로 쓴다.

- 구세대 코드가 신세대 포맷의 파일을 만나면 "손상"으로 판정하고 `s_bReady = false`로 자기를 정지시킨다. 이 세대에는 레지스트리(HKLM) 폴백이 없어 복구 경로 자체가 없다.
- 반대로 신세대 코드가 구세대 포맷의 파일을 만나면 `ERROR_NOT_REGISTRY_FILE`(1017)을 인지해 `.corrupt`로 보존한 뒤 저장소를 재구축한다.

이 비대칭이 사고의 본체다. 버전이 올라가는 방향은 안전하게 처리되지만, 내려가는 방향은 막혀 있었다.

세대를 가르는 경계는 다음과 같다.

```
APPSTORE_SINCE_VERSION  = 1.6.242.481   // 파일 저장소 도입 (텍스트 INI)
APPSTORE_HIVE_SINCE     = 1.6.242.499   // 하이브 도입
```

| 버전대 | 저장소 형태 | 하이브 파일을 만나면 | 판정 |
|---|---|---|---|
| 499 이상 | 레지스트리 하이브 | 정상적으로 연다 | 안전 |
| 481 ~ 498 | 텍스트 INI | "손상"으로 판정 → 전면 정지 | 위험 |
| 481 미만 | HKLM 직접 사용 | `registry.ini`를 모른다. 미러를 읽는다 | 안전 |

하향 배포 자체는 회사가 허용한 정책이라 방향을 막는 것은 해법이 아니다. 위험한 구간은 481~498뿐이고, 499 이상 버전끼리는 어느 방향으로 오르내려도 안전하다.

## 값은 잃지 않았다

저장소가 멈춘 시점에도 `HKLM\SOFTWARE\ORANGE`의 미러 값은 온전했다. `DeviceID`, `DeviceTicket`, `UpdateUrl`이 모두 살아 있었다. 즉 데이터 손실이 아니라 접근 거부였고, 499 이상 버전으로 다시 덮으면 즉시 원상 복구된다.

## 조치

증상의 재발 자체를 막는 작업과, 저장소 설계의 구조적 비대칭을 해소하는 작업을 나눠서 진행하기로 했다.

**배포 패키지 세대 정렬 (즉시 조치)**

모든 서버의 배포 패키지를 1.6.242.499 이상으로 맞춘다. 사고 당시 서버 하나가 498을 배포하고 있었고, 그 서버로 옮겨가는 것만으로 위험 구간에 진입했다. 하향 배포 정책은 그대로 둔 채 재발을 막는 가장 빠른 조치다.

**저장소 포맷을 하향 안전하게**

포맷을 바꿀 때 파일 이름도 함께 바꾸는 방안을 검토한다. 하이브를 다른 이름으로 분리하면 되돌아온 구버전 빌드는 "파일 없음"을 만나 HKLM에서 정상적으로 마이그레이션한다. 대안으로는 패키지 메타데이터에 저장소 스키마 세대를 싣고, 현재 빌드가 자기보다 낮은 세대로 내려갈 때 그 세대가 읽을 수 있는 형태로 저장소를 되돌려 놓고 넘기는 방법도 있다. 앞으로 나갈 빌드부터는 못 읽는 저장소 파일을 만나면 HKLM으로 폴백하도록 하되, 이미 현장에 나간 498 버전에는 소급 효과가 없다.

**저장소 쓰기 실패를 호출부에 알린다**

서버 주소를 저장하는 함수(`CAgentParams::SetServerOverride`)가 저장 실패 반환값을 그대로 버리고 있었다. 실패를 호출한 쪽에 돌려주고, UI에서 저장을 시도한 경로에서는 사용자에게 그 실패를 알리도록 고친다. 지금은 저장 버튼을 눌러도 실패가 사용자에게 전달되지 않는다.

**서버 선택 로직 결함 정리**

등록 함수(`RegisterToServer2`)가 어떤 서버로 등록이 성공했는지 확인하지 않고 지정 서버(`ServerOverride`)를 승격하거나 삭제하는 구조도 발견됐다. 지정한 서버가 실패하고 다른 서버가 성공해도 지정값이 소진돼 버린다. 후보 목록을 비우는 코드가 없어 "없애야 한다"는 주석만 남고 실제 구현은 없는 채로, 쓰이지 않는 변수만 남아 있는 자리도 있었다. 관리자가 UI로 지정한 주소와 공장 기본값이 한 필드에 겹쳐 있어 생기는 문제라, 두 값의 의미를 분리하는 작업이 필요하다.

**세대 역행 감지 및 기록**

지금의 다운그레이드 감지 함수(`IsDowngraded`)는 이번 유형의 사고를 잡지 못한다. 저장소 자체가 손상돼 조기 반환하는 경로에서는 비교가 이뤄지지 않기 때문이다. 필요한 비교는 "실행 중인 바이너리의 버전"과 "저장소에 적힌 버전"이고, 저장소를 못 열었을 때도 HKLM의 부트스트랩 값만으로 판정할 수 있어야 한다. 하향 자체는 정상 동작이므로 목표는 거부가 아니라 경고와 서버 보고다.

**계측 보강**

재발 여부를 빠르게 판단하기 위해 로그 지점을 늘린다. 서버 주소 저장 성공·실패와 그 값, 지정 서버 후보가 빈 이유가 "값 없음"인지 "못 읽음"인지, 완성된 서버 후보 목록과 각 후보의 출처, 승격 시 어떤 서버가 성공했는지, 기동 시 저장소 상태(경로, 파일 매직, 세대, 버전)를 한 줄로 남기는 로그, `set.SETTINGS` 수신 시 그 명령이 로컬 UI에서 왔는지 매니저 서버에서 왔는지 구분하는 로그를 추가하기로 했다. 지금은 로컬과 원격 발신이 로그에서 구분되지 않는다.

## 확인 계획

- 각 서버의 패키지 배포 버전이 1.6.242.499 이상인지 확인한다
- 499 이상 빌드가 설치된 PC에 498 패키지를 내려서, 설치 로그에 저장소 재오픈 성공이 찍히는지 확인한다(저장소가 손상 처리되면 실패)
- UI에서 서버를 바꾼 뒤 로그에 지정값 저장 → 후보 1순위로 시도 → 등록 성공 → 지정값에서 기본값으로 승격이라는 순서가 모두 찍히는지 확인한다
- 지정한 서버를 일부러 불통 상태로 둔 뒤 다른 서버가 붙었을 때도 지정값이 남아 있는지 확인한다(사라지면 실패)
- 저장소를 일부러 손상시킨 상태에서 서버 변경을 시도했을 때, 로그만 보고 "1순위 후보가 왜 비었는지"를 추론 없이 판정할 수 있는지 확인한다

증상 1(서버가 UI 조작 없이 공장 기본값으로 바뀐 경로)의 발신자 규명은 위 작업들을 정리한 뒤 마지막 순서로 진행한다.
